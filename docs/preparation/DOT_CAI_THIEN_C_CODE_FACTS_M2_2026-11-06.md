# Đợt cải thiện C, M2 (IPA + audio): code facts (06/11/2026)

Read-only survey of the worktree `.claude/worktrees/dot-cai-thien-c` (branch `docs/dot-cai-thien-c`, HEAD `0bd3eac6`) for the M2
decision: per-sense IPA (UK, US) shown Cambridge-style; one optional free-form IPA on private words; admin edits IPA per sense;

## A1. Content model, revisions, publish

**Models** (`apps/api/prisma/models/content.prisma`):

- `Entry` (38–64): `lemma` VarChar(100), `pos`, `scope` `catalog | private`, `ownerUserId` (private only). Uniqueness is two hand-written
  partial indexes (comment 60–62).
- `EntryLevel` (79–93): `entryId`, `level`, `sourceId` → `DataSource`, `basis`.
- `Sense` (95–115): `entryId`, `contextLabel`, `state` (default `open`), `liveRevisionId` (the published revision), `replacesSenseId`,
  `stateChangedBy/At`. No content columns at all.
- `SenseRevision` (117–147): `revisionNo`, `status` (`draft` → `reviewed` / `rejected` → `published` / `superseded`), `draftSource`
  (`ui | csv | user | ai_suggestion`), `contentHash`, `examples[]`, `topicCodes[]`, `acceptedForms[]`, `formOfEntryId`, `formKind`,
  reviewer/publisher columns.
- `SenseRevisionText` (149–159): key `(revisionId, language, kind)`; today only `(vi, gloss)` and `(en, definition)` are written.
- Private words are **not a separate model**: an `Entry` with `scope = 'private'` plus normal `Sense` / `SenseRevision` rows.

**Where IPA fits.** All editable sense content lives on `SenseRevision` (+ `SenseRevisionText`); `Sense` holds only identity and state.
Every learner read joins `s.live_revision_id` (e.g. `content/words/words.service.ts:105`, `content/learner/learner-content.service.ts:123`).
INFERENCE: IPA belongs on `SenseRevision` (two nullable columns, e.g. `ipa_uk`, `ipa_us`) so it is drafted, reviewed, published and
reverted like the rest of the content. Putting it on `Sense` would bypass review/publish and would show unpublished edits immediately.

**Revision content shape** (`apps/api/src/content/senses/revision-content.ts`):
- `RevisionContent` (13–21): `glossVi, definitionEn, examplesEn, topicCodes, acceptedForms, formOf?`.
- `normalizeContent` (35–62), `mergeContent` (64–73: a field absent from the patch inherits the base).
- `contentHash` (75–82). Note line 79: `formOf` joins the hash **only when set**, "so every revision stored before D29 keeps its hash".
  IPA must follow the same trick, or every existing revision hash changes and the "unchanged" shortcuts misfire.

**Revision on admin edit** (`apps/api/src/content/senses/senses.service.ts`):
- `revisionData` (47–57) is the single place a catalog revision's columns are built from `RevisionContent` (texts, examples, topics,
  accepted forms, form-of). A new field must be added here.
- `createSense` (62–88) creates revision 1 as `draft`.
- `saveDraft` (90–123): reads latest revision; base is the last non-rejected one (100–102); merges the patch (114); if the hash is
  unchanged returns `changed: false` (115–117); otherwise marks open `draft/reviewed` revisions `superseded` (118) and creates
  `revisionNo + 1` as `draft` (119–121). **All fields are copied by `readContent` (29–36) → `mergeContent` → `revisionData`.**
- `readContent` is duplicated in three places that would each need the IPA field: `senses.service.ts:29`,
  `senses/import-content.ts:27`, `private/private-words.service.ts:68`.

**Publish** (`apps/api/src/content/senses/publish.service.ts`):
- `publishRevision` (90–128): checks state, stale revision, rejected/superseded, `publishViolations` (gloss, example, level; 26–37), then
  supersedes the old live revision (118–120), sets the revision `published` (121–123) and `sense.liveRevisionId` (124–126). No content is
  copied on publish: the live pointer moves to an existing revision.
- Entry points: `publishItem` (48–51, used by `POST /v1/admin/content/senses/publish` and by the publish job), `quickPublish` (61–76:
  saveDraft + publish in one transaction), `unpublish` / `retire` (53–59, change `state` only, keep `liveRevisionId`, 142).
- `writeSense` (78–88) only accepts catalog senses (`entry: { scope: 'catalog' }`, 80).
- The only other writer of `liveRevisionId` is the private-word path (`private-words.service.ts:123–125`); found with
  `grep "liveRevisionId:"` over `apps/api/src` (non-spec).

## B5. Background jobs

- **Generic job framework** (`apps/api/src/content-pipeline/jobs/`):
  - Queue names are a closed union `JobQueueName = 'content-import' | 'content-publish' | 'content-inflections'` (`job-types.ts:3`); the
    reconciler has its own hard-coded list (`job-reconciler.service.ts:10`). A new queue must be added in both.
  - Durable row `BackgroundJob` (`apps/api/prisma/models/pipeline.prisma:1–24`): `queue, status, exclusiveKey` (partial unique WHERE
    `status='running'`, migration `20261012180000_pipeline/migration.sql:107`), `attempts`, lease columns, **`createdBy` uuid required**,
    **`operationId` uuid required**. Per-kind detail tables share its id (`ImportBatch` 26–47, `PublishJob` 100–112, `PublishJobItem` 114–126).
  - Enqueue: `job-queue.service.ts:62–75` — BullMQ `add` with `jobId` = row id, `attempts: IMPORT_JOB_ATTEMPTS` (default 3, `app-config.ts:251`),
    exponential backoff `IMPORT_JOB_BACKOFF_MS` (5 s, 254) with jitter 0.5, remove on complete/fail. Queue prefix `JOB_QUEUE_PREFIX`
    (default `wordmet`, `app-config.ts:253`; `.env.example:17`), used at `job-queue.service.ts:45`.
  - Runner (`job-runner.service.ts`): one Worker per registered queue, own Redis connection, `concurrency: 1` (39–53); lease acquire,
    heartbeat (58–67); retry decision uses both BullMQ's count and the stored `attempts` (76–88).
  - Lease reconciler (`job-reconciler.service.ts:32–74`): every `IMPORT_RECONCILE_SECONDS` (30 s) re-enqueues `queued` rows and
    expired `running` rows, or fails them after max attempts (43–56).
  - Handlers register themselves in `onModuleInit` (`job-handler.registry.ts:9`; example `publish/publish-job.handler.ts:28–30`).
- **Publish job** (`content-pipeline/publish/publish-job.handler.ts:32–80`): loops `PublishJobItem` rows `pending` and calls
  `ContentService.publishItem` per sense (53–55), stores the outcome (56–58). This is the bulk path; single publish and quick-publish do
  not use a job (A1).
- **Hook point "after a sense is published"**: every catalog publish passes `PublishService.publishRevision` returning
  `{ outcome: 'published' }` (`content/senses/publish.service.ts:127`), inside the entry-lock transaction. Private words publish in
  `PrivateWordsService.publishRevision` (`private-words.service.ts:109–126`). INFERENCE: the cleanest hook is in the callers after the
  transaction commits (`publishItem` 48–51, `quickPublish` 61–76, private create/update), so an enqueue failure never rolls back a
  publish and the reconciler/backfill picks up missed rows.
- **Two other queue patterns exist** (dedicated BullMQ queue + own Worker, no `background_jobs` row): `ai-eval`
  (`ai/eval/eval-queue.service.ts:11, 15–52`) and reminders (`notifications/scheduler/reminder-queue.service.ts:54–63`). Both gate the
  Worker on `pipeline.runWorkers`.
- **Worker process**: `apps/api/src/worker.ts:6–17` boots the same `AppModule` with `pipeline.runWorkers: true`; every Worker above starts
  only then (`job-runner.service.ts:36`, `eval-queue.service.ts:43`). `pnpm build` then `pnpm start:worker` runs `dist/worker.js`
  (CLAUDE.md "Local setup").

## Surprises / conflicts with the planned behaviour

1. **Example sentences are voiced today.** `SpeakSentence` reads catalog examples (`Flashcard.tsx:97`, `SenseBlock.tsx:85`) and saved
   sentences (`Flashcard.tsx:109`, `LearningBlock.tsx:51`, `SavedSentencesDialog.tsx:74`) with the browser voice. "Example sentences are
   NOT voiced" must say whether these browser buttons stay (likely: only no Google file) or go.
2. **Private-text privacy rule vs Google TTS.** `SpeakSentence private` deliberately uses only a local voice (`SpeakButtons.tsx:49`) so
   the learner's text never leaves the device. Sending private words to Google is a new flow of learner content to a third party; the
   privacy draft's processor list (`chinh-sach-bao-mat.draft.md:134–139`, branch `docs/launch-b-legal-drafts`) has no TTS entry, and line
   188 says Wordmet does not send Google "từ vựng của bạn" (in the AdSense paragraph). Both need updating.
3. **Private word IPA: entry or sense?** A private word can have several senses (labels p2, p3: `private-words.service.ts:162–166`); the
   PATCH has entry-level fields and per-sense fields (`my-words.schemas.ts:11–22`). "One optional IPA field" fits the entry level, but
   all content lives per revision; storing it on `Entry` breaks that pattern, storing it per sense means copying it to every sense.
4. **Word page has one speaker for the whole page** (`WordPage.tsx:72`), and a lemma's page mixes catalog and private senses of several
   POS. Cambridge-style per-POS/per-sense IPA + audio means new UI per `SenseBlock` or per POS section.
5. **No UK button exists** (owner removed it 27/10/2026, `SpeakButtons.tsx:34`); M2 brings UK back as a Google file. The fallback for a
   pending UK file needs a UK browser voice, which many devices lack (`uk` may be null, `speech.ts:47`).
6. **The job framework is batch-shaped.** `background_jobs` needs `created_by` and `operation_id` (`pipeline.prisma:10–11`), queue names
   are a closed union plus a second hard-coded list (`job-types.ts:3`, `job-reconciler.service.ts:10`), and each Worker runs
   `concurrency: 1`. One job per word would mean ~17.600 rows for the catalog backfill; a per-batch job or the dedicated-queue pattern
   (`ai-eval`, reminders) may fit better. Decision for the design.
7. **Publish happens in four code paths** (single publish, quick-publish, bulk publish job, private create/update), all inside entry or
   owner lock transactions (`publish.service.ts:78–88`, `private-words.service.ts:109`). An enqueue inside them would run before commit.
   CSV import never publishes (drafts only), so "generate on publish" also covers imported words.
8. **`contentHash` stability**: adding IPA to the hash for every revision changes all stored hashes; follow the `formOf` precedent
   (`revision-content.ts:79`).
9. **CSP only applies in production builds** (`app-csp.ts:28`): a missing `media-src` will not show in `next dev`, only in the
   production build/e2e (`pnpm cf:docker` on Windows).
10. **No object storage, no Google Cloud SDK, no storage emulator in Docker** (C7): the local stack, CI and the smoke need a fake
    storage and a fake TTS, following the `AI_FAKE_ENABLED` + production-guard pattern.
11. **Sources page cannot list an IPA source automatically** (D10): the rule keys on `entry_levels` and AGID only.
12. **Account deletion**: private-word content is erased by `content/private/account-eraser.provider.ts:10–19`; audio files of private
    words in object storage would need their own deletion (not covered by the DB cascade).
