## 8. Surprises (contradictions and traps)

1. **Ôn has no screen of its own.** `/app/recall` is `PracticeSession` with `recall={{groupId}}` (`RecallSession.tsx:20`; `PracticeSession.tsx:39`). Question card, `Choices`, `TypeWordInput`, `AnswerFeedback`, header, `Progress` are practice-session code that M5a (practice session) restyles. M5b cannot restyle Ôn without either waiting for M5a's `AnswerOption`/`QuestionCard`/`TypeWordInput` or editing the same files. `RecallSummary` also imports `STAGGER` from `review/ReviewSummary` and `useSummary` from `practice/session/SessionSummary`. Ownership and order of M5a vs M5b must be fixed in the plan.
2. **Design §8.2 row "Ôn (flashcard)" is stale after GM17.** The flashcard stack, drag and piles (motion §2) belong to Học (`/app/review`); Ôn (`/app/recall`) is MCQ/type and has no stack motion. Design §9 M5 table already says Học for review; §8.2 and the motion doc ("Màn Ôn (lật thẻ…)") still say Ôn.
3. **The stack, drag, stamps, piles, chips and counters do not exist in code.** Flashcard is one card with a static `-rotate-2` sibling (`Flashcard.tsx:50`); no pointer handlers anywhere; no `WordChip`. M5b Học is a new component set, not a restyle. Design §8.5 (drag with two buttons, WCAG 2.5.7) is already satisfied by the existing buttons and keys 1/2.
4. **Flip number mismatches beyond design §8.3.** Code 280 ms `--ease-standard` (`globals.css:209`); `Flashcard.tsx:34` comment still says "420ms"; motion says 300 ms main curve and `perspective: 1400px` but Tailwind `perspective-distant` is 1200 px (4.3.3 theme) so a custom value or token is needed. Prototype flips both ways (Space toggles, button "Xem mặt trước", `chong-the-mo.html:274-280,272`) but code `flip()` only sets true (`use-review-queue.ts:86`); `ReviewSession.tsx:49-51` Space on a flipped card does nothing. Decision needed: allow flip back?
5. **Prototype keys vs code.** Prototype also accepts ArrowLeft/ArrowRight (`chong-the-mo.html:428-429`); code has Space, 1, 2, Esc, Enter (summary) only. Figma/design mention only 1/2 (kbd chips). Decision needed (ArrowLeft/Right would clash with nothing in code but are new).
6. **Answering before flip.** Code: answer buttons are not rendered until flipped (`ReviewSession.tsx:95-111`) and `answer()` silently returns (`use-review-queue.ts:53`), pinned by test `review-session.test.tsx:151`. Prototype/motion §2 show both answer buttons `aria-disabled`, a shake (300 ms) and the line "Lật thẻ để xem nghĩa trước đã." when pressed early. Moving to the prototype changes a pinned behaviour.
7. **Network-first vs animation-first.** The card advances only after `POST /v1/reviews` returns (`use-review-queue.ts:60-67`), with one-at-a-time gating (`busyRef`, pinned by test `:311`) and same-`review_id` retry on `NetworkError` (E19, tests `:159`, `:184`). The prototype dissolves instantly and promotes the next card at once, and its note says a fast second press is accepted (`chong-the-mo.html:176`). Starting the dissolve before the POST resolves would need optimistic advance plus a way to bring the card back on failure; starting it after adds latency before the dissolve. Decision needed; it conflicts with the existing tests.
8. **Summary timing has three values.** Motion doc 520 ms/90 ms, design §8.3 400 ms/90 ms, code 250 ms/50 ms with `STAGGER` delays 0/50/100/150/200 (`ReviewSummary.tsx:9-15`) pinned by tests `review-session.test.tsx:131-135` and used by `RecallSummary` and `SessionSummary`. Changing it moves three screens and their tests; the prototype also lists words per pile on the summary, which code does not (`ReviewSummary` shows counts only).
9. **Reduced-motion rule kills the specified fallback.** Motion §8 keeps `opacity` 140 ms (dissolve) and 160 ms (face swap); `globals.css:503-515` forces all CSS animation/transition durations to 0.01 ms with `!important`, so a CSS-driven fade would be instant. The prototype's reduced path uses WAAPI `el.animate` (`:371`) and CSS opacity transitions only inside its own `.rm` class. Keep WAAPI or add an exception to the global rule; design §8.4 says keep both existing mechanisms.
10. **Phone blur is capped at 12 px, the dissolve is 18 px.** `--blur-wm-lg` is 12 px under 48rem (`globals.css:45-50`); using the token gives 12 px on phones, the prototype's 18 px only on desktop. Design §8.1 allows this; the perf measurement (20-card Học on low-end Android/iOS, 4–6× CPU slowdown, record frame numbers in the delivery record) has no existing harness in e2e.
11. **Opaque wrapper hides the dot grid.** Both screens wrap content in `min-h-dvh bg-canvas` (`ReviewSession.tsx:118`, `PracticeSession.tsx:161`; `--color-canvas #f1f3fd`) inside `(focus)/layout`, whose `DotGridBackground` is `fixed -z-10` (`layout.app.tsx:8`). The opaque div paints over it (not render-verified). The new screens must drop that background.
12. **Progress UI differs three ways.** Code: phone-only bar (`translateX`) plus "còn N thẻ" on md (`ReviewSession.tsx:133-149`), pinned by `data-testid="review-progress"` transform `-50%`/`0%` (test `:116`); prototype: one tick per card coloured by result; Figma (app-redesign-plan `:447`): continuous bar filled to the current card with no chips. `ProgressBar` does not exist in `ui/`.
13. **Stamp/pile text needs data the UI does not hold.** "lên ngăn {X}" and "về ngăn 1 ngày" (`chong-the-mo.html:225-226`) need the stage name from `card.level` + 1 (`Card.level` exists in the queue type, `groups-api.ts:53-58`) and the fixed rule "needs review goes to stage 1 day" (also in `review.doneBody`); the API result of `POST /v1/reviews` (level, due_date) is ignored by the hook today. New vi/en strings are required (none of the nudge, flip-back, drag hint, pile or stamp copy exists in `App.review`).
14. **Stack renders more cards than the code fetches forms for.** `Flashcard` calls `useForms` (GET `/v1/words/{lemma}`) per mounted card (`Flashcard.tsx:40`). A 4-deep live stack would fire 4 requests per step and mount 4 `PronunciationLine`s (speech/audio hooks); the prototype mounts 4 full cards (`chong-the-mo.html:248`). Behind cards should render a light front only.
15. **`touch-action: none` vs a tall back face.** Prototype sets it on the card (`:59`) to own the gesture; the back face here can hold meaning, forms, example and several saved sentences (`Flashcard.tsx:67-115`, `min-h-80`) and `overflow-hidden`, so on a phone vertical scroll over the card would be blocked. Needs `touch-action: pan-y` or a scroll area decision. Also `StreakToast` (`bottom-28` on phone) must not sit on the new answer buttons/piles; it is mounted in `AppProviders` and imported from `app-ui/` by both hooks, so it stays in the old UI until M8 moves it.
16. **GM19 (exact typing) needs no code.** Matching is server-only and already exact after normalization (`apps/api/src/practice/grading/normalize.ts:2-21`). What is missing is a test that pins it from the UI side and the Figma "so chữ" line, which can only be drawn after reveal (the correct word is not sent on `try_again`), and the "Làm lại / Gợi ý / Xem đáp án" repeat-try loop has no Figma frame (Figma shows wrong → compare).
